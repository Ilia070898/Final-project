# პროექტის ახსნა და წარდგენა

## 1. პროექტის მიზანი

ეს არის ონლაინ რესტორნის სასწავლო ვებაპლიკაცია. მომხმარებელს შეუძლია კერძების ნახვა, კატეგორიითა და ინგრედიენტებით გაფილტვრა, კალათაში დამატება, რაოდენობის შეცვლა და წაშლა. ასევე დამატებულია რეგისტრაცია, შესვლა და გამოსვლა. რეალური გადახდა არ ხდება.

პროექტში გამოიყენება Python, Django, HTML და CSS. JavaScript არ გამოიყენება. ყოველი ფორმის გაგზავნის შემდეგ სერვერი ამუშავებს მოთხოვნას და ბრაუზერში განახლებული გვერდი იტვირთება.

## 2. სად ინახება მონაცემები

ორი განსხვავებული წყარო გვაქვს:

| მონაცემი | წყარო |
|---|---|
| კერძები, ფასები, კატეგორიები | IT Step-ის გარე API |
| კალათა | იგივე API; შეიძლება საერთო იყოს სხვა სტუდენტებთან |
| მომხმარებლები და პაროლის ჰეშები | პროექტის SQLite ბაზა |
| ავტორიზაციის სესიები | Django-ს სესიები, ბაზა და ბრაუზერის cookie |

რეგისტრაცია საერთო API კალათას ინდივიდუალურად არ აქცევს. API-ს კალათის ენდპოინტები მომხმარებლის ნომერს არ იღებს. ეს შეზღუდვა წარდგენაზეც უნდა ვიცოდეთ.

## 4. მენიუს გვერდის გახსნა

ბრაუზერი აგზავნის GET მოთხოვნას მთავარ მისამართზე. config/urls.py მას menu/urls.py-ს გადასცემს. იქ ცარიელი გზა დაკავშირებულია catalog ფუნქციასთან.

catalog იღებს კატეგორიებს და ქმნის FilterForm-ს. თუ მომხმარებელს ფილტრები არ აურჩევია, იტვირთება ყველა კერძი. თუ არჩეულია, is_valid ამოწმებს მნიშვნელობებს. api_params ტოვებს მხოლოდ შევსებულ ველებს; ნულოვანი სიცხარე არ იკარგება, რადგან 0 სწორი არჩევანია.

api.products მონაცემებს გარე სერვერისგან იღებს. render ფუნქცია შაბლონს გადასცემს context ლექსიკონს. HTML-ში for ციკლი თითოეულ კერძზე ქმნის ქარდს. if განსაზღვრავს, რომელი წარწერა გამოჩნდება თხილეულსა და ვეგეტარიანულობაზე.

## 5. დამატება და რაოდენობის შეცვლა

„დამატების“ ფორმა POST მოთხოვნას აგზავნის კერძის ნომრის შემცველ მისამართზე. add ფუნქცია კატალოგში ეძებს კერძს, შემდეგ კალათაში ეძებს იმავე ნომერს. თუ კერძი უკვე იყო, რაოდენობას უმატებს ერთს; თუ ახალია, რაოდენობა ხდება 1.

ფორმიდან ფასს არ ვიღებთ. ფასს ვკითხულობთ გარე კატალოგიდან, რათა მომხმარებელმა ბრაუზერში საკუთარი ფასი ვერ მიუთითოს.

write_basket ახალი ჩანაწერისთვის POST მოთხოვნას აგზავნის, განახლებისთვის კი PUT-ს. ეს განსხვავდება ბრაუზერის ფორმისგან: ბრაუზერი Django-სთან იყენებს POST-ს, ხოლო Django გარე API-ს საჭირო HTTP მეთოდით ესაუბრება.

reply ინახავს შეტყობინებას და redirect-ით კალათის გვერდზე გადადის. შემდეგი GET ახალი კალათის მდგომარეობას აჩვენებს. ამ მიდგომით წარმატებული POST-ის შემდეგ გვერდის ჩვეულებრივი განახლება იმავე ფორმას ავტომატურად აღარ აგზავნის.

რაოდენობის ფორმაში IntegerField იღებს მხოლოდ მთელ რიცხვს 1-დან 99-მდე. არასწორი მნიშვნელობა API-ში არ იგზავნება. წაშლა ცალკე POST ფორმიდან იწყება, შემდეგ Python API-ს DELETE მოთხოვნას უგზავნის.

## 6. თანხის გამოთვლა

cart_state თითოეული ჩანაწერის ფასს ამრავლებს რაოდენობაზე. მაგალითად, 9.50 × 2 = 19.00. შემდეგ ყველა ჩანაწერის თანხა ემატება total-ს. პორციების რაოდენობა გროვდება count-ში.

Decimal გამოიყენება ათობითი თანხების გამოთვლისთვის. floatformat:2 შაბლონში მხოლოდ ორ ათწილადს აჩვენებს; ის შეკვეთის ჯამს არ ითვლის.

## 7. რეგისტრაცია და შესვლა

RegistrationForm მემკვიდრეობით იღებს UserCreationForm-ის შესაძლებლობებს. ჩვენ ვამატებთ სახელსა და ელფოსტას და ვცვლით წარწერებს. Django ამოწმებს მომხმარებლის სახელის უნიკალურობას, პაროლების თანხვედრას და კონფიგურაციაში ჩართულ პაროლის წესებს.

GET-ზე register ქმნის ცარიელ ფორმას. POST-ზე ქმნის ფორმას გამოგზავნილი მონაცემებით. თუ is_valid სწორია, form.save მომხმარებელს ბაზაში ინახავს. პაროლი ინახება ჰეშის სახით; ჩვეულებრივი ტექსტი ბაზაში არ ინახება. ჰეშირება არ ნიშნავს შექცევად დაშიფვრას.

auth_login ქმნის ავტორიზებულ სესიას. შემდეგ გვერდებზე request.user ამოიცნობს მომხმარებელს. ელფოსტა მხოლოდ ინახება: დამადასტურებელი წერილი არ იგზავნება.

შესვლას Django-ს LoginView მართავს, გამოსვლას — LogoutView. as_view კლასს URL-ისთვის გამოსაყენებელ დამმუშავებლად გარდაქმნის. ამ კლასების გამოყენება სილაბუსის CBV თემას შეესაბამება.

## 8. შეცდომების დამუშავება და დაცვა

try/except იჭერს API-სთან კავშირის ან პასუხის მოსალოდნელ პრობლემას. მომხმარებელი იღებს განმარტებას. API-ზე ჩაწერა ავტომატურად არ მეორდება: შეიძლება სერვერმა უკვე შეინახა ცვლილება და მხოლოდ პასუხი დაიკარგა.

require_POST კრძალავს შეცვლას GET მოთხოვნით. csrf_token და Django-ს middleware ფორმის გაგზავნისას იცავს უცხო საიტიდან გაყალბებული მოთხოვნებისგან. ვალიდაცია სრულდება სერვერზეც; HTML ველის მინიმუმისა და მაქსიმუმის მითითება მარტო საკმარისი არ არის.

## 9. ORM და DRF — ზუსტად რა გვაქვს

Django-ს მზა User და Session მოდელები უკვე ORM-სა და მიგრაციებს იყენებს. ამიტომ migrate აუცილებელია. პროექტს საკუთარი კერძის ან შეკვეთის მოდელი არ აქვს: დავალებით მათი წყარო გარე API-ა. ამ ვერსიაში არც ადმინისტრატორის პანელი არის ჩართული.

გარე REST API-ის გამოყენება არ ნიშნავს საკუთარი REST API-ის შექმნას. api.py არის კლიენტი. Django REST Framework, serializer-ები და ჩვენი საკუთარი REST CRUD ენდპოინტები ამ პროექტში არ გამოიყენება. მათ გამოყენებას ნუ მიაწერ პროექტს მხოლოდ იმიტომ, რომ სილაბუსში გაიარეთ.
